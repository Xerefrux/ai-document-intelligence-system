# Evaluation report

This is what I measured, how, and what is wrong with the measurement. Every number below comes from a command in the last section, and the raw output of each run is saved in `evaluation/results/`. Nothing here is estimated unless it says "estimate".

**The short version.** On the synthetic documents I generated, digital PDFs and spreadsheets are read without a single wrong value after my fixes, scans are read well when they are clean and badly when they are not, and the system flags most of what it gets wrong instead of hiding it. Two things keep these numbers from meaning much outside this test set: the documents are synthetic and were made by the same working session that wrote the extractor, and the one time I tested on layouts the extractor had never seen, it scored clearly lower (table in "The first blind run"). I would expect real invoices to land closer to that lower result than to the 100% rows.

## What was measured

### The test documents

Everything is generated by code in `evaluation/synth`, with invented companies, addresses, products and amounts. The generator writes each file and, next to it, the true values that are printed on that file. Two sets, made from different layouts:

| | Development set | Holdout set |
|---|---|---|
| Layouts | six (T1 to T6), differing in label wording, number format (US, European, South Asian digit grouping), date format and where the currency appears; T3 is a narrow till receipt | four more (H1 to H4), written after I stopped changing the extractor: a serif "tax invoice" (H1), a till receipt with quantity and price on a second line (H2), a boxed "Bill" grid with "M/s" before the customer (H3), and a modern layout with each label above its value (H4) |
| Files | 204 (190 valid, 14 deliberately broken) | 176 (162 valid, 14 deliberately broken) |
| Invoices (records) | 258 | 235 |
| Line items | 987 | 833 |
| Digital PDFs | 60 | 40 |
| Scans (PDF, JPG, PNG, TIFF) | 24: 8 light, 8 medium, 8 heavy damage | 16: 6 light, 5 medium, 5 heavy |
| Spreadsheets (xlsx, xls, csv) | 18, in four layouts: invoice sheet, ledger with one invoice per row, one row per line item, workbook with several sheets | 18, same four layouts, different header wording |
| PDFs with several invoices | 4 (15 invoices) | 4 (15 invoices) |
| Invoices with one injected mistake | 32 (8 kinds, 4 each) | 32 |
| Duplicate tests | 52 | 52 |

Scans are made by drawing the page and then damaging it: light is slight skew and noise, medium adds blur and lower resolution, heavy adds strong blur, noise and skew together. The damage is simulated by my own code. It is not the output of a real scanner or a phone camera.

### Definitions

- **Field accuracy** (called "micro" in the raw reports): of all the headline fields that are printed on the documents, the share the system read correctly. The headline fields are invoice number, invoice date, supplier, customer, subtotal, tax, total and currency. Amounts must match to within 0.01, names and numbers are compared after removing case and punctuation, dates must match exactly. A record that was not found at all counts every field as wrong. Due date is scored in the error listings but not in this figure.
- **Whole document right** (called "strict"): every headline field correct, nothing invented, and every line item right, including quantity and unit price.
- **Invented values**: of the fields that are not printed on the document, the share where the system still returned a value.
- **Line item F1**: a predicted line counts as correct when its description is close and its amount matches exactly. Precision and recall over all lines, then F1.
- **Silent error**: a document with a wrong or invented headline value that was not sent to manual review. These are the dangerous ones.
- **Flagged for review**: the document has no records, or at least one record with an error or a warning.
- **Success rate** and **failure rate**: the share of valid files that finished processing and the share that crashed or failed. This is about the pipeline running, not about the values being right. Files that are broken on purpose are reported separately.
- **Seconds per file**: wall time from the start of processing to the saved result, measured with two files processed at the same time on a two core machine.

### How it was run

Linux, Python 3.13, two CPU cores, Tesseract 5.3.4 for the main scan figures and RapidOCR 1.2.3 for a second set. Extraction in `rules` mode, which never calls an AI. No AI service was reachable where I worked, so **there is no measurement of the AI extraction path in this report**. Two files at a time (`--jobs 2`).

### Scans, by how damaged they are

This is where the real weakness is, and the averages above hide it.

| OCR engine | Set | Light | Medium | Heavy |
|---|---|---|---|---|
| Tesseract | development (8, 8, 8) | 96.8% | 88.3% | 3.4% |
| Tesseract | holdout (6, 5, 5) | 95.7% | 65.8% | 0.0% |
| RapidOCR | development | 95.2% | 80.0% | 10.2% |
| RapidOCR | holdout | 97.9% | 76.3% | 27.5% |

(Field accuracy. "Whole document right" on light scans is much lower, 17% to 83% depending on the set and engine, because one slip anywhere on the page, such as a missed currency or a customer name that lost its space, fails the whole document.)

Reading this honestly:

- **Light scans are fine, heavy scans are not readable**, and the system says so. With Tesseract, every heavy scan in both sets (8 and 5) was sent to manual review, and none returned a confident wrong value in the holdout set. In the development set a few heavy scans did return an invented value (a currency, a customer name made from noise), which is the 18.2% in the table; all of those came from heavy scans, and all of those documents were flagged.
- **The two OCR engines are about equal here.** Tesseract is better on the development scans, RapidOCR on the holdout scans. With 16 and 24 files per set, a single file moves a rate by 4 to 6 points, so I do not read the gap as a real difference. I chose Tesseract as the default from early spot checks, and these results do not show it was clearly the right call. Without Tesseract installed, the system uses RapidOCR and works.
- **File format does not matter much.** With Tesseract, field accuracy by format ranges from 47% to 67% (JPG, PDF, PNG, TIFF) and the order changes between the two sets. Each format has only 4 to 6 files, so this is noise.
- **Scans fail on small things.** The most common error on light and medium scans is a missed or mangled field (a currency, a customer name with its spaces eaten, a due date). The most worrying is a wrong character inside an invoice number: Tesseract read `SI-25-477` as `S1-25-477` and `SI-25-679` as `$1-25-679`. Nothing in the document tells a rule that this is wrong, so those two documents were not flagged.

|---|---|---|---|---|

The two Tesseract errors are the invoice number slips described above (a letter read as a digit). The four RapidOCR errors are all names that lost their spaces on blurred text (`AlphaElectronicsEnterprise` for `Alpha Electronics Enterprise`), which a person would still recognise but which does not match the truth. Of the scans that did contain a wrong value, 6 of 6 (development) and 5 of 7 (holdout) were flagged for review with Tesseract, and 8 of 10 and 6 of 8 with RapidOCR.

### Sent to manual review

Of the files that are supposed to be clean (digital PDFs, PDFs with several invoices, scans and spreadsheets), **19 of 106 in the development set and 18 of 78 in the holdout set** ended up in the review queue (Tesseract run).

| | Development | Holdout |
|---|---|---|
| Digital PDFs | 0 of 60 | 0 of 40 |
| PDFs with several invoices | 0 of 4 | 0 of 4 |
| Scans | 14 of 24 (light 2, medium 4, heavy 8) | 10 of 16 (light 2, medium 3, heavy 5) |
| Spreadsheets | 5 of 18 | 8 of 18 |

The spreadsheet number is **not a fair result** and I want to be plain about why. The values in those files were all read exactly as printed (field accuracy is 100% above). They were flagged because my spreadsheet generator wrote files that do not add up: the invoice sheets print a total that includes a discount or a shipping charge but have no row for it, the grouped sheets print an invoice total that includes tax without a tax column, and one grouped layout has no total at all. The system reported the mismatch or the missing total, which is the correct thing to do with such a file, but these are poor test documents and they inflate the review rate. I found this on the last day, after the full evaluation had been run, and I left the data as it was rather than change it again. None of the spreadsheet files that do add up was flagged, so a fair review rate for spreadsheets would be near 0. That would put the overall figures at roughly 14 of 106 and 10 of 78, and I would say it is an estimate, not a measurement.

### Validation, duplicates and broken files, through the real API

`python -m evaluation.e2e` uploads the files through `POST /api/documents`, lets a worker process them, and then checks what the API reports. Digital PDFs only, no scans, so it runs in seconds (158 files in 8.0 s for the development set, 138 in 7.5 s for the holdout set).

| Check | Development | Holdout |
|---|---|---|
| Injected mistakes that raised the expected validation code (wrong total, wrong subtotal, wrong tax, wrong line amount, missing invoice number, missing date, due date before invoice date, ambiguous date) | 31 of 31 | 30 of 30 |
| Exact same file uploaded twice: refused at upload | 10 of 10 | 10 of 10 |
| Same invoice number and supplier, different layout: `DUPLICATE_INVOICE` | 10 of 10 | 10 of 10 |
| Same supplier, date and total, new number: `POSSIBLE_DUPLICATE` | 10 of 10 | 10 of 10 |
| Look alike invoices that must not be flagged as duplicates | 12 of 12 not flagged | 12 of 12 not flagged |
| The original of a duplicate pair is never flagged | 10 of 10 | 10 of 10 |
| Broken or hostile files that ended where they should | 14 of 14 | 14 of 14 |
| Clean digital invoices sent to manual review | 0 of 60 | 0 of 40 |

The 14 broken files per set: 4 refused at upload with a specific code (random bytes named `.pdf`, a Windows executable renamed `.pdf`, binary data named `.csv`, a zero byte file); 3 that contain no invoice (a letter, a white page, a spreadsheet with a header and no rows), which complete with nothing extracted, and with a `NO_INVOICE_DETECTED` warning where there was a page to judge, so a person can see they were not skipped; and 7 that fail with a code and are not retried because retrying cannot help (a truncated PDF, a PDF with a scrambled middle, a password protected PDF, a truncated workbook, a truncated JPEG, a damaged PNG, and a 30000 by 30000 pixel image that is tiny on disk and 900 megapixels once decoded).

One thing to know about the fault check: a few faults cannot be shown by a layout (a layout with no due date printed cannot show a due date before the invoice date). The generator records whether each fault actually appears on the page, and the check counts only those that do: 1 file was left out in the development set and 2 in the holdout set.

### Speed

| What | Measurement |
|---|---|
| Digital PDF, one page, one invoice | median 0.01 s per file (0.006 s per page) |
| **One PDF of 1000 pages with 434 invoices** (1.7 MB, text layer), upload to searchable | **14.9 s**, about 67 pages per second, single worker, 187 MB peak memory. 434 of 434 invoice numbers and 434 of 434 totals right, nothing flagged. |
| Searches on that database (434 records, 1000 pages) | 13 to 26 ms for keyword, 18 ms for hybrid |
| Scan, Tesseract | median 1.18 s (development) and 7.52 s (holdout); 90th percentile 16.9 s and 18.9 s; slowest 19.0 s and 19.8 s |
| Scan, RapidOCR | median 5.32 s and 5.03 s; 90th percentile 12.9 s and 8.7 s; slowest 16.3 s |

I ran the whole evaluation twice, before and after fixing a thread safety bug in PDF reading (see the reliability notes in `docs/ARCHITECTURE.md`). The accuracy figures were identical both times. Timings moved by a few tenths of a second at the median (the development scan median was 0.89 s the first time and 1.18 s the second), which gives a feeling for the run to run noise. The tables show the second run; the RapidOCR figures are from the first.

The big difference between the two Tesseract medians is the retry logic. When a page reads poorly the system tries rotations and clean-ups, up to a budget of 15 seconds per page (`DOCINTEL_OCR_RETRY_BUDGET_SECONDS`), so a hopeless page costs about 15 to 20 seconds and a clean page about a second. The holdout set has more middling scans, so more of them spend time on retries.

**A scanned PDF of 1000 pages was not measured.** My estimate: with the per page times above and two pages processed at once, the Tesseract scans average 6.1 s (development) and 8.9 s (holdout) per page, which gives roughly 50 to 75 minutes for 1000 pages on this two core machine, with RapidOCR about the same. It would be faster with more cores, because OCR runs in a pool of processes, and slower if the pages are worse than my test pages. The 1000 page figure above is for a digital PDF made by combining generated invoices, not a real 1000 page report.

## The first blind run

After the extractor was frozen I wrote four new layouts (H1 to H4, a different look for each) and ran the system on them once, before changing anything. That run is saved untouched in `evaluation/results/holdout_first_run.txt`, with the raw predictions in `holdout_predictions_first_run.json`.

| Group (holdout, first run) | Files | Field accuracy | Whole document right | Line item F1 |
|---|---|---|---|---|
| Digital PDFs | 40 | 96.7% | 50.0% | 0.874 |
| PDFs with several invoices | 4 | 97.4% | 53.3% | 0.825 |
| Spreadsheets | 18 | 90.6% | 52.2% | 1.000 |
| Scans (Tesseract) | 16 | 52.0% | 12.5% | 0.500 |

Field accuracy looked fine and whole document accuracy was half. What was behind it:

- **Layout H2 (a narrow till receipt, quantity and price on a second line under each item): no line item was read in any of its files.** Whole document accuracy on that layout was 0%.
- **Layout H3: the customer name was missed in 10 of 10 files.** It was written after "M/s", a label the extractor did not know.
- **Spreadsheet ledgers:** the invoice date was read for only 35% of rows and the currency for about half, because the holdout files use header words the extractor had never seen ("Issued", "Doc date", "Curr").
- **Scans** behaved as on the development set: fine when light, poor when damaged.

Extractor changes I made afterwards, because of what that run showed:

1. A reader for receipts that put the quantity and unit price on the line under the item name.
2. Reading the numbers of a table row in column order when the row has as many numbers as the table has numeric columns, because headers are often left aligned over right aligned numbers and the nearest header can be the wrong one.
3. "M/s" and "Messrs" as customer labels.
4. More header words for ledgers: invoice date ("Issued", "Doc date") and currency ("Curr").

These changes are why the holdout rows in the main table are 100% and why they are not blind. They are the same kind of fix I did on the development set, and I did not look for more cases of the same kind in new layouts afterwards, so the first run is the best evidence I have for how the extractor does on a layout it has not seen: **about 97% of fields right, but only half of the documents completely right.**

## Mistakes in my own test data

Reading the error listings, several "extractor errors" turned out to be errors in my data. Each was fixed and the whole evaluation was rerun on the corrected data. The numbers in this report are all from the corrected data, and the first blind run was made before these fixes.

1. **Sheets with formulas.** The generator wrote total formulas that ignored a discount or shipping charge on the invoice, so the recalculated total did not match the label. It now writes plain values for invoices that have either.
2. **Missing shipping row.** Layouts T3 and T6 added shipping to the total but never printed a shipping row. Six of 60 "clean" invoices were flagged `TOTAL_MISMATCH`. The extractor was right and the page was wrong. Both layouts now print the row.
3. **Mistakes that cannot be seen.** Some injected mistakes did not appear on some layouts, and were counted as missed. Each fault file now records whether the fault was actually drawn, and only those count.
4. **Lost broken files.** Two broken files with the same name and different extensions (`truncated.pdf`, `truncated.xlsx`) shared an id and one overwrote the other. The id now includes the extension.

Two real flaws in the extractor also came out of this, both fixed with regression tests:

- A line such as `Invoice No Date 25/07/2025` produced the invoice number `Date 25/07/2025`, an invented value. The number cleaner now drops a leading label word.
- The text `INV-2025` was parsed as an amount of minus 2025 (a currency code "INV" and a number). Three letter prefixes and suffixes are now accepted only when they are real ISO currency codes. This second fix was made after the first blind run.

**Still wrong in the data and left as it is:** the spreadsheet layouts that print totals that do not add up (see "Sent to manual review").

## What these numbers do not tell you

- **They come from synthetic documents written by the same author as the extractor.** The extractor has implicitly learned what my generator produces. Layouts I did not think of, real logos, stamps, handwriting, odd fonts, rotated pages, coffee stains, languages other than English and scripts other than Latin are not represented.
- **The holdout is blind only for the first run.** After that it was used for fixing, like the development set.
- **Sample sizes are small.** 16 to 24 scans per set and 40 to 60 digital PDFs. A single file is worth 4 to 6 points on a scan rate.
- **The scan damage is simulated.** Real scans have different failure modes, and I would expect the real distribution to be messier.
- **The AI extraction path is not measured at all,** and neither are the hosted embedding services. Accuracy of semantic search was not measured either (the default search vectors are a character n-gram hash, which handles typos and word endings and not meaning). Search is covered by the automated tests and by the timings above, not by a relevance score.
- **Timings are from a two core sandbox,** not production hardware, with two files at a time.
- **The 1000 page figure is for a digital PDF.** A scanned one was not run.

## Reproduce

```bash
pip install -e ".[dev]"
python -m evaluation.build --split dev     --out evaluation/dataset      # generates the files and the truth
python -m evaluation.build --split holdout --out evaluation/dataset
python -m evaluation.extract_run --split dev     --jobs 2                # about a minute and a half each
python -m evaluation.extract_run --split holdout --jobs 2
python -m evaluation.report --split dev     --errors 60                  # tables and error listings
python -m evaluation.report --split holdout --errors 60
python -m evaluation.extract_run --split holdout --groups scan --jobs 2 --set ocr_engine=rapidocr --out evaluation/work/holdout_scans_rapidocr.json
python -m evaluation.report --split holdout --groups scan --predictions evaluation/work/holdout_scans_rapidocr.json
python -m evaluation.e2e --split holdout                                 # validation, duplicates and broken files through the API
python -m evaluation.build --perf --out evaluation/dataset               # the 1000 page PDF
python -W ignore -m evaluation.perf
```

The generator is seeded, so the same command gives the same documents and the same true values. Saved outputs:

| File | What it is |
|---|---|
| `evaluation/results/dev_report.txt`, `holdout_report.txt` | the full tables and error listings (Tesseract) |
| `evaluation/results/dev_scans_rapidocr_report.txt`, `holdout_scans_rapidocr_report.txt` | the same for scans with RapidOCR |
| `evaluation/results/holdout_first_run.txt`, `holdout_predictions_first_run.json` | the first blind run, untouched |
| `evaluation/results/e2e_dev.txt`, `e2e_holdout.txt` (and `.json`) | validation, duplicates and broken files through the API |
| `evaluation/results/perf_text_1000p.json` | the 1000 page run |

To measure the AI path, set `GEMINI_API_KEY` (or `OPENAI_API_KEY` and `OPENAI_MODEL`) and rerun `extract_run` with `--set extraction_mode=hybrid`, then compare the report with the one above. I have not done this.
